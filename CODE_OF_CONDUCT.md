# Unicorn Project Code of Conduct

## Our Commitment

The Unicorn Project is committed to providing a professional, respectful, inclusive, and technically constructive environment for everyone who participates.

Contributors, users, maintainers, reviewers, researchers, students, and other participants are expected to interact respectfully and professionally.

The purpose of this Code of Conduct is not to prevent disagreement. Technical disagreement, critical review, and open discussion are important parts of software engineering and open-source development. The goal is to keep such discussions focused on ideas, implementations, evidence, and technical merit rather than becoming personal or hostile.

## Expected Behaviour

Participants are expected to:

- Treat other participants with respect and professionalism.
- Discuss technical disagreements based on facts, evidence, standards, specifications, tests, and reproducible results.
- Give constructive criticism of code, architecture, documentation, and design decisions.
- Accept constructive criticism of their own contributions.
- Clearly distinguish facts, assumptions, opinions, and experimental results.
- Respect different levels of experience and technical backgrounds.
- Help new contributors understand the project where reasonably possible.
- Respect intellectual property, licenses, copyrights, and attribution requirements.
- Handle security-related information responsibly.
- Avoid publishing sensitive information, private keys, credentials, certificates containing private information, or other confidential material.
- Report suspected security vulnerabilities responsibly rather than exploiting or unnecessarily publicizing them.
- Follow applicable laws and regulations when using or contributing to the project.

## Technical Discussion

Unichorn deals with security-sensitive technologies including PKI, digital signatures, certificates, trust infrastructures, cryptographic devices, and related standards.

Technical claims should therefore be open to critical examination.

Participants are encouraged to:

- reference relevant RFC, ETSI, OASIS, W3C, ISO, or other applicable specifications;
- provide test cases where possible;
- document interoperability problems;
- identify security assumptions explicitly;
- distinguish implementation support from formal standards compliance or certification;
- challenge technical decisions when there is a reasonable engineering or security argument for doing so.

Strong technical disagreement is acceptable.

Personal attacks are not.

## Unacceptable Behaviour

The following behaviour is considered unacceptable:

- Personal insults or attacks.
- Harassment or intimidation.
- Threats or incitement of violence.
- Discriminatory or degrading comments.
- Deliberate disruption of technical discussions.
- Repeated trolling or intentionally inflammatory behavior.
- Publishing another person's private information without permission.
- Impersonating contributors, maintainers, organizations, or other individuals.
- Knowingly submitting malicious code.
- Deliberately introducing security vulnerabilities or backdoors.
- Attempting to obtain credentials, private keys, tokens, or other secrets from project participants.
- Using project communication channels for spam or unrelated commercial advertising.
- Knowingly making materially false claims about the project's security properties, certification, or regulatory status.

## Security-Related Conduct

Because Unichorn contains cryptographic and PKI functionality, responsible security behavior is particularly important.

If you discover a potential security vulnerability:

1. Do not exploit the vulnerability against systems or data for which you do not have explicit authorization.
2. Do not publish private keys, passwords, credentials, tokens, or confidential certificate information.
3. Provide enough technical information for the issue to be reproduced and investigated.
4. Allow a reasonable period for analysis and remediation before public disclosure when responsible disclosure is appropriate.
5. Clearly distinguish confirmed vulnerabilities from suspected or theoretical issues.

Security research performed against your own systems or with explicit authorization is welcome.

## Scope

This Code of Conduct applies to project-related interaction in:

- GitHub issues;
- pull requests;
- code reviews;
- discussions;
- project documentation;
- project-related e-mail communication;
- other communication channels officially associated with Unichorn.

It may also apply when an individual is publicly representing the project.

## Enforcement

Project maintainers are responsible for interpreting and enforcing this Code of Conduct.

Depending on the circumstances and severity of a violation, maintainers may:

- request that inappropriate behavior stop;
- remove or edit inappropriate comments where the platform permits it;
- close or lock discussions;
- reject contributions;
- temporarily restrict participation; or
- permanently ban an individual from project-controlled communication channels.

Report security incidents, credible threats, or potentially unlawful conduct to the appropriate platform operators or authorities where necessary.

Enforcement decisions should be proportionate to the behavior involved and should not be used merely to suppress legitimate technical criticism or disagreement.

## Reporting

You may report conduct issues to the project maintainer through an appropriate private contact channel provided by the project or the maintainer's GitHub profile.

For ordinary technical disagreements, bugs, feature requests, interoperability problems, and non-sensitive security discussions, please use the appropriate GitHub issue or discussion mechanism.

Do not place passwords, private keys, authentication tokens, confidential certificates, or other secrets in a public GitHub issue.

## Good-Faith Participation

Mistakes and misunderstandings happen.

Where appropriate, participants should be allowed to clarify statements, correct mistakes, or change inappropriate behavior.

At the same time, repeated or deliberate violations do not have to be tolerated merely because they are presented as technical disagreement.

## Independence of Technical Decisions

Financial sponsorship, organizational affiliation, professional status, or the volume of contributions does not exempt anyone from this Code of Conduct or grant special authority over security or technical conclusions.

Technical decisions should be based primarily on:

- correctness;
- security;
- interoperability;
- maintainability;
- applicable standards;
- reproducible evidence; and
- the long-term interests of the project.
